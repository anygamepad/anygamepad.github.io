# Device reports

A device report is what one app saw of one physical controller: the web
tester, or the desktop app's collection mode. The same JSON document is a
file on the desktop, an entry in the browser's IndexedDB, the body of a
GitHub issue, and later what the sync server stores
([ADR 0007](../../docs/adr/0007-local-first-device-reports.md)). Reports
feed the curated profiles in [`data/profiles/`](../profiles/README.md).

The format is defined by the Rust types of
[`anygamepad-report`](../../crates/anygamepad-report) (roadmap task P1),
which every app and tool uses to build, scrub, validate and read reports.

| File | What |
|------|------|
| [`schema.json`](schema.json) | JSON Schema of the format, generated from the types and published at <https://anygamepad.github.io/schema/report.json>. It checks the structure; `Report::validate` checks the rest (below). |
| [`example.json`](example.json) | An illustrative report, not a recording: a DualSense over USB in Chrome on Windows, seen through the Gamepad API and WebHID. Generated by the crate's tests. |

Regenerate both after changing the types:

```sh
UPDATE_SCHEMA=1 cargo test -p anygamepad-report --all-features --test schema
```

## Fields

| Field | What |
|-------|------|
| `format` | Always `anygamepad-device-report`. |
| `schema_version` | Format version, `1`. A reader rejects versions it does not know. |
| `created` | Day the report was made, UTC (`YYYY-MM-DD`). No time of day: the day tells which browser and library were current, and correlates less. |
| `source` | `app` (`web` or `desktop`), `app_version`, `library_version`. |
| `host` | `os`; `os_version` from the desktop app (a release such as `14.6.1` or `6.8.0-45-generic`, never a host name); `browser` (engine and major version) for web reports. |
| `user` | What the person says: `product`, the controller in their words (at most 100 characters); `mode`, the mode they say it is in (`xinput`, `dinput`, `switch`, `ps3`, `ps4`, `ps5`, `xbox`, `android`, `apple`, `keyboard_mouse`, `other`); `missing_buttons` and `missing_axes`, the controls they said it does not have in the guided wizard. Optional. |
| `views` | One per provider or browser API that sees the device, 1 to 8. |

Each view:

| Field | What |
|-------|------|
| `identity` | The `DeviceIdentity` of the model: provider, backend, OS, transport, IDs, names, driver, descriptor hash, browser, Gamepad API `id` and `mapping`. |
| `fingerprint` | The identity's fingerprint (16 hexadecimal digits), to group reports of the same kind of device. Must match the identity. |
| `family` | The family the library recognized, if any. |
| `profile` | The name of the device profile the library picked, if any. |
| `layout` | The raw elements the provider reads (`RawLayout`): buttons, axes with their ranges, hats, sensors, touchpads, battery. |
| `outputs` | Outputs the provider can drive. |
| `capabilities` | Canonical controls the library derives, when it maps the view. |
| `hid` | For HID views: `descriptor` (hexadecimal, when readable; its hash is the identity's `descriptor_hash`), `collections` (the report structure, as WebHID gives it), `input_samples` (the first input report of each ID and length, at most 8, hexadecimal data). |
| `confirmed` | The mapping the person confirmed in the guided wizard, in the [profile format](../profiles/README.md#inputs) with inputs naming elements of `layout`, and no `when`. |

Unknown fields are errors everywhere: nothing the format does not know is
stored or passed on.

## Privacy

Reports never contain serial numbers, Bluetooth MAC addresses or other
personal data. Identities exclude them by construction (no serial field, no
device paths). On top of that, clients run `Report::scrub` and every reader
runs `Report::validate`, which rejects:

- 12 or more hexadecimal digits in a row in any text, possibly split by `:`
  or `-` (Bluetooth addresses, serial numbers, UUIDs); `scrub` replaces them
  with `[redacted]`;
- email addresses, control characters, and texts above 256 characters;
- input samples of reports that can carry identifiers (Nintendo `0x21` and
  `0x81`).

`scrub` recomputes the fingerprint of a view whose identity it changed. A
name a person gave their device cannot be told from a product name, so the
apps show the whole report before it is shared.

Consent texts, retention and the handling of shared reports are in
[`docs/privacy/`](../../docs/privacy/README.md) (roadmap task P3); the
public policy is <https://anygamepad.github.io/privacy/>.

## Limits

| What | At most |
|------|--------:|
| Compact JSON of a report (fits a GitHub issue) | 60,000 bytes |
| Views | 8 |
| Texts from devices and OSes | 256 characters |
| `user.product` | 100 characters |
| Buttons, axes, hats or touchpads per layout, each | 256 |
| Input samples per view | 8 |
| Bytes per input sample | 1,024 |
| Report descriptor | 4,096 bytes |
| HID collection nesting | 8 levels |
| HID collections, reports, items and usages per view | 2,048 |
