# H5: Test mode in the desktop app

- Status: completed
- Roadmap: ROADMAP/2026-10-31/ (task ID: H5)

## Goal

The desktop app's test mode (ADR 0008), with the web app's flow (H4): the
list of controllers, the ways to connect a picked one, detection of a pad
connected without picking (Confirm, Choose another), a session of the
library's test runner, and the anonymous report reviewed and saved to
`test-reports/`. Plus the virtual output suite (A5): each virtual pad type
reads back what it shows through the app's own provider, and a game's
vibration sent to it reaches the pad under test; skipped with a reason
where the machine cannot create virtual pads.

## Decisions

- The session runs in the device worker, not the UI. Reason: the window
  repaints on demand, so its frames are no clock; the worker polls every
  4 ms and owns the provider and the virtual pads.
- The worker feeds the session on new input, and every 20 ms at rest.
  Reason: evdev reports changes only, and the session's timers (rest,
  release) need updates while the pad is still; `updates_per_second` then
  measures the pad, not the poll loop.
- The virtual pad check is scripted (known states, each read back), not a
  comparison with the pad under test. Reason: deterministic and covering
  every control of each type, with no person needed; the pad under test
  takes part through the vibration step and the copy after the check, as
  the app's virtual pads work.
- Virtual pad commands have their own queue (`take_virtual_commands`)
  rather than following the prompt. Reason: the first and last commands
  of a step are sent in the update that changes the prompt, so routing by
  prompt misses them.
- A machine that cannot create virtual pads gets `not_applicable` with
  the reason ("no /dev/uhid", "no permission to write /dev/uinput", "no
  virtual pads on this OS yet"), the same as an output the API cannot
  drive. Reasons are fixed texts, so reports carry no paths beyond the
  device nodes' names.
- The Switch Pro Controller type gets no vibration step: its HD rumble is
  not emulated yet (A5).
- In ANYGAMEPAD_DEMO mode the demo pad follows the session's prompts.
  Reason: a session can run end to end on any OS and in CI.
- A pad connected when the Test page first shows is detected like one
  connected while it shows. Reason: the owner's flow (connect without
  picking, see what was detected), and the app usually starts with the
  pad plugged in.
- The unit picked last is remembered per model while the app runs, not
  in the settings file. Reason: enough for a campaign; persisting it can
  come with F4.

## Open questions

- Not tried with real pads, `/dev/uinput` or `/dev/uhid`: the read-back
  through `xpad`, `hid-playstation` and `hid-nintendo` (and LinuxProvider
  showing those devices) is first tried in H6. A type whose controls the
  driver or the Linux mapping do not give back (the DualSense's touchpad
  click, the Switch Pro Controller's capture button) will fail, which is
  what the check is for.
- The test reports' `updates_per_second` differs between apps (the web
  counts frames); H7 or H8 may want the rate of input reports or events
  instead.
- The page does not draw the controller with the control asked for
  highlighted yet (also open for H4).
