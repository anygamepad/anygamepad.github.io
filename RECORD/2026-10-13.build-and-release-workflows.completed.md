# Build and release workflows

- Status: completed
- Roadmap: ROADMAP/2026-10-10/ (no task ID: follows F1's CI and W1's web
  pipeline; C10 will add crate publishing)

## Goal

Owner request: a `build.yml` workflow that runs the tests and the builds,
and a manual `release.yml` that raises the version (major, minor or patch),
runs `build.yml`, creates a GitHub release and attaches the builds.

## Done

- `.github/workflows/build.yml`: the jobs of the former `ci.yml` (fmt,
  native on three OSes, wasm with browser tests and the `.d.ts` check,
  MSRV) and `web.yml` (web app and bindings build, size budget, smoke test,
  Pages deployment on pushes to `main`, now only after every job passed).
  Artifacts of every run: `web` (the built site) and `wasm-bindings`.
  Callable (`workflow_call`) with a `version` input that each building job
  applies to its tree first.
- `.github/workflows/release.yml` (`workflow_dispatch`, input `bump`:
  patch, minor, major; main only): `prepare` computes the version and
  refuses an existing tag; `build` calls `build.yml` with it; `release`
  commits `Release vX.Y.Z`, tags `vX.Y.Z`, pushes both atomically to main,
  zips the artifacts (with the license files) and publishes the release with
  generated notes, `anygamepad-web-vX.Y.Z.zip`,
  `anygamepad-wasm-vX.Y.Z.zip` and `SHA256SUMS`.
- `scripts/version.mjs` (no dependencies): `current`, `next`, `set`,
  `check` over the 14 places that hold the version (`Cargo.toml` workspace
  version and internal dependency requirements, the workspace members in
  `Cargo.lock`, `apps/web/package.json` and `package-lock.json`). `build.yml`
  checks that they agree.
- `ci.yml` and `web.yml` removed (their jobs live in `build.yml`).
- Verified locally: actionlint 1.7.7 on both workflows; `version.mjs`
  round trip (0.0.0 to 0.1.0 and back is byte-identical; `cargo metadata
  --locked` and `npm ci --dry-run` accept the bumped lockfiles); the release
  job's commit, tag and packaging steps in a throwaway clone (zips and
  checksums verified). The workflows themselves only run on GitHub.

## Decisions

- One `build.yml` instead of keeping `ci.yml` and `web.yml` beside it.
  Reason: they would run the same tests twice on every push.
- The release builds the bumped tree first and pushes the commit and the
  tag only after the build passed, in one atomic push. Reason: a failed
  build or a push rejected because main moved leaves no stray tag or
  commit, and the release can be run again; the commit is the same tree the
  build tested (same base commit, same deterministic `version.mjs set`).
- Version applied in the tree (`version` input of `build.yml`) rather than
  a temporary branch. Reason: nothing is pushed before the build passes.
- Assets: the built site and the WebAssembly bindings, the only builds the
  project has so far. Native libraries have no binary artifact; the
  desktop app (A9/A10) and crate packages (C10) will be added when they
  exist.
- The release job's `build` call grants `pages: write` and `id-token:
  write`. Reason: GitHub checks a reusable workflow's job permissions
  against the caller even for jobs that will not run (the Pages job only
  runs on pushes to main).
- The workflow-level concurrency group includes the workflow name. Reason:
  in a nested run `github.workflow` is the caller's, so a release's build
  does not cancel, or get cancelled by, a push build of main.

## Open questions

- Release needs GitHub Actions to be allowed to push to `main` and create
  tags: a branch protection rule on `main` must let `github-actions[bot]`
  bypass it, or the release push fails (nothing is published then).
- The release commit is pushed with `GITHUB_TOKEN`, which starts no
  workflow, so GitHub Pages keeps showing the previous version number until
  the next push to main. Deploying Pages from the release is possible if
  wanted.
- Pre-1.0 releases are published as normal releases, not pre-releases.
