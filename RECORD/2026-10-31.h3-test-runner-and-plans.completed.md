# H3: Test runner and test plans

- Status: completed
- Roadmap: ROADMAP/2026-10-31/ (task ID: H3)

## Goal

The sans-IO runner every test mode shares (ADR 0008): it runs a plan's
steps on the device under test, checks what it can by itself, asks the
person the rest, records the evidence, and writes the test report (H1).
Plans are data.

## Done

- `anygamepad_db::plan`: `TestPlan` (ID, version, name, description,
  steps), `PlanStep` (flat: `id`, `check`, optional `side`, `seconds`,
  `tolerance`, validated against the check), `CheckKind` (detection,
  buttons, stick_rest, stick_circle, trigger_pull, rate, motion_rest,
  motion_turn, touchpad, battery, rumble, lightbar, player_leds, hotplug),
  `Side`; TOML, JSON Schema; embedded at build time
  (`TestPlan::embedded`, `TestPlan::get`).
- `data/test-plans/`: `quick.toml` (detection, every button), `full.toml`
  (every check), README with the steps, `schema.json`; the web build
  publishes `/schema/test-plan.json`.
- `anygamepad::testing` (feature `testing`): `Session::new(SessionSetup)`
  (plan, catalog model, configuration, device report, drivable outputs,
  whether the app feeds HID reports) expands the plan for the model in
  the confirmed mode (one step per button; nothing for what the model
  lacks; not applicable when the API cannot read or drive it).
  `update(raw, canonical, now)`, `input_report`, `removed`, `added`,
  `answer`, `skip`, `not_on_this_pad`, `repeat`; `status()` gives the
  `Prompt` (with English `text` naming face buttons as printed);
  `take_commands()` the output commands; `finish()` the scrubbed report.
  Every input step first waits for the pad to be released; button steps
  end on release and fail with what answered instead (a canonical button,
  or a raw input in the profile syntax); south and east together mean
  "not on this pad" (also added to the device report's missing buttons);
  questions are answered on the screen or the pad (south yes, east no,
  north not sure). Evidence: raw states that changed, or HID input reports
  (identifying ones never kept), from the step's start to its end.
- CI: clippy and tests of `anygamepad` with `testing`, clippy on wasm32,
  `cargo +1.85 check`.
- Tests: plan validation and embedding; `tests/plans.rs` (schema, files,
  round trip, unknown checks); `tests/testing.rs`: a simulated person
  follows the prompts of Quick and Full on a standard pad (every step
  passes), a decoded DualSense read over HID (buttons including mute and
  the touchpad click, sticks, triggers, rate in reports per second, motion
  at rest with gravity on `accel_y+`, a turn on `gyro_y+`, touchpad,
  battery, rumble, light bar, player lights, hotplug; evidence as input
  reports), a pad that lacks two buttons (not applicable, missing buttons
  recorded), a pad whose mapping swaps south and east (both fail, each
  naming the other), a detection mismatch, skips, a bad setup. Every
  report validates.

## Decisions

- Plan steps are flat structures rather than tagged enums. Reason: the
  embedded copy is postcard, which cannot read internally tagged enums;
  flat steps read the same in TOML, postcard and the JSON Schema, and
  `validate` checks the parameters fit their check.
- The runner reads the canonical state the app's mapping gives, plus the
  raw state for evidence and for naming what answered when nothing
  canonical did. Reason: the test is of what a game would get; the raw
  input shows what to fix.
- Steps for controls the model lacks are left out, not reported. Reason:
  shorter sessions and reports; the catalog says what the model has.
- Motion checks follow the canonical frame (X right, Y up out of the
  face, Z towards the player): flat and face up reads `accel_y+`; turning
  left is `gyro_y+`. A provider that disagrees fails, which is what C4
  and C7 need to find out on real pads.
- Output tests are scripts of commands at fixed times (700 ms each), then
  a question. Reason: the same for every app, and repeatable.
- `testing` is an optional feature of `anygamepad`. Reason: games do not
  need the report format.
- The detection step runs on the confirmed configuration: it fails when
  detection proposed something else, or when the catalog has identities
  for the mode and transport and none matches; it does not apply when
  neither can be compared.

## Open questions

- The thresholds (stick tolerance 0.15, reach 0.9, trigger 0.95, gyro rest
  0.05 rad/s, gravity within 1 m/s²) are first guesses, to tune with the
  first campaign (H6).
- "Back" (redo the previous step) is not implemented; skip and repeat
  are.
- The virtual output suite belongs to the desktop test mode (H5).
