# C6: macOS native provider (IOKit HID + GameController)

- Status: WIP
- Roadmap: ROADMAP/2026-11-11/ (task ID: C6; status update in place)

## Goal

The native provider on macOS: IOKit's `IOHIDManager` for HID game
controllers, and the GameController framework for the pads macOS drives
itself (PlayStation, Xbox, Switch Pro, MFi), which it switches to reports
IOKit readers of the standard report cannot use (research note 06).

## Done

- Platform-independent parts, tested on Linux:
  - `native::hid::HidPad`: a pad read through a native raw HID API, either
    driven by its C7 `HidDriver` or generic, read through its report
    descriptor with `anygamepad-hid`'s `RawReader` (latest value of every
    element kept across reports). Meant for Windows HID (C5) as well.
  - `native::iokit`: the matching usages (Generic Desktop Joystick, Game
    Pad, Multi-axis Controller), the property keys read (and only those),
    `transport()`, `game_controller_drives()` and `takes()`,
    `HidProperties::identity()`, and `IOReturn` codes to provider errors.
  - `native::game_controller`: product categories, the extended gamepad's
    buttons with their canonical names (`GcButton`), `GcPad` (layout,
    outputs, `fill` from a `GcSnapshot`), touch points, battery, the
    motion frame conversion, identity.
- `native::macos` (`cfg(target_os = "macos")`, `#![allow(unsafe_code)]`,
  every `unsafe` block with its `// SAFETY:`):
  - `IoHidProvider`: an `IOHIDManager` matching the game controller
    usages, scheduled on the creating thread's run loop in a private mode
    (`org.anygamepad.iokit`) that `update` and `poll` run without
    blocking; the device set compared every 250 ms; per open device, an
    input report callback and a removal callback writing to a sink
    allocated with the device and freed after unregistering; feature
    reads (`IOHIDDeviceGetReport`) and output reports
    (`IOHIDDeviceSetReport`) for the drivers; `Exclusive` seizes the
    device; `Shared` starts the driver; rumble stopped on close;
    `inaccessible()` counts the devices macOS refused to open.
    `set_game_controller_pads(true)` also takes the pads GameController
    drives.
  - `GameControllerProvider` (macOS 11.3 or later): `GCController`
    controllers with an extended gamepad, compared every 250 ms; the
    profile objects looked up once; buttons, sticks, triggers, the
    DualSense and DualShock 4 touchpads, Xbox paddles and share button,
    motion (sensors turned on while open), battery; light bar and player
    index outputs; `set_background_events` for
    `shouldMonitorBackgroundEvents`. Calls wrapped in autorelease pools.
- `examples/macos_pads.rs`: both providers (or `--iokit` alone with the
  drivers), canonical state on button changes, motion while south is
  held, lights on east; runs the main run loop between polls.
- macOS-only tests (`native::macos::tests`): start both providers, list,
  open, poll and close what they see. CI's macOS runners run them, so
  the IOKit and GameController calls run on a real macOS even without
  pads.
- Dependencies, macOS only, behind the `native` feature: `objc2` 0.6,
  `objc2-core-foundation`, `objc2-io-kit` (`hid`) and
  `objc2-game-controller` 0.3.2, default features off. `anygamepad-hid`
  becomes an optional dependency of `anygamepad` (feature `native`); the
  web bundle is unchanged (only symbol names differ in the raw `.wasm`).

## Decisions

- Two providers, as on Linux (evdev and hidraw). Reason: GameController
  is macOS's own driver for the pads it knows, like the kernel's on
  Linux; IOKit with the protocol drivers is the library driving them,
  which apps opt into.
- The IOKit provider leaves the pads GameController drives to it by
  default (PlayStation from the DualShock 4 on, Xbox, Switch Pro).
  Reason: GameController switches the PlayStation pads to their extended
  report and owns their outputs; one owner per pad until C12 arbitrates.
- A private run loop mode pumped from `update` and `poll`, no thread of
  its own. Reason: no locks or channels around IOKit's callbacks, and no
  blocking; the cost is that the provider is not `Send` and must be
  created on the thread that drives it (as SDL's IOKit backend does).
- The manager is never opened; each device is opened on `open`. Reason:
  `IOHIDManagerOpen` opens every matched device, and the access mode
  (seize or not) is per device.
- Raw input reports, not IOKit element values. Reason: the protocol
  drivers and `anygamepad-hid` read reports, as on hidraw and WebHID, and
  element values miss the PlayStation pads' extended reports.
- GameController buttons as canonical sources (`button:south`, ...).
  Reason: GameController names them by position already; the mapping
  engine needs no profile and a profile can still correct one.
- Identity of GameController pads: `vendorName` as the product name (the
  name Safari shows), the product category as the driver, no VID/PID or
  transport. Reason: GameController does not tell them; guessing IDs from
  the category would put made-up data into reports.
- Motion: one sample per poll when the reading changed, stamped with the
  provider's clock. Reason: polling GameController gives the latest
  reading only, with no sensor clock; value-changed handlers would need
  blocks and a queue.
- The GameController provider requires macOS 11.3. Reason: the DualSense
  profile class (`GCDualSenseGamepad`) appeared then, and looking up a
  missing class panics.
- `LocationID` is the device's container. Reason: `DeviceLocation`
  documents it so; it is never serialized.
- Not wired into the desktop app. Reason: its worker needs a
  `Provider + Send`, and these providers must be created on the worker's
  thread; that change is A2's.

## Open questions

- Everything about real devices: whether IOKit delivers the PlayStation
  pads' extended reports while GameController drives them, whether macOS
  asks for Input Monitoring for game controllers, GameController's motion
  frame and signs, the touchpad's vertical direction, `buttonA` on a
  Switch Pro Controller, the product category strings other than
  `"DualSense"` (`native::game_controller` lists them).
- Whether `GCController.controllers()` sees pads from a thread other than
  the main one while an app's main run loop runs (the desktop app's
  worker).
