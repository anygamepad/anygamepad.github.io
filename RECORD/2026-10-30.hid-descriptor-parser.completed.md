# HID report descriptor parser and report reader

- Status: completed
- Roadmap: ROADMAP/2026-10-14/ (no task ID: owner request of 2026-10-30,
  not planned yet; groundwork for C4-C7 and the collection mode)

## Goal

Parse raw HID report descriptors into the structure WebHID gives
(`HidCollection`), and read input reports into the raw elements the
mapping engine (C3) consumes, sans-IO. Native backends need it to compare
their view of a device with the web one (P1 reports carry `descriptor` and
`collections`), and airHID (the owner's ESP32 wireless HID project) needs it
to read game controllers from a USB host, where only the descriptor and the
raw reports exist.

## Done

- New crate `anygamepad-hid`, depending only on `anygamepad-model`.
- `Descriptor::parse`: short and long items, global stack (`Push`/`Pop`),
  extended (4-byte) usages, usage ranges, report IDs, unit system and
  exponent, collections nested as WebHID nests them (items in the
  innermost open collection, reports sorted by ID). Every main item is also
  a `HidField` with its bit offset in its report and the usage of its
  top-level collection, since `HidCollection` loses the order of items that
  interleave with child collections.
- `HidField::read` (any bit alignment, 1 to 32 bits, sign-extended when the
  logical minimum is negative), `usage` (variable items) and `array_usage`
  (array items).
- `RawReader`: lists a game controller's buttons, axes and hats as a
  `RawLayout` named by `RawSource::Hid`, and fills a `RawState` from each
  report without allocating. Accepts reports with the ID byte first (USB,
  HID APIs) or split (WebHID).
- Tests: HID 1.11 boot keyboard and boot mouse, hand-built game pads (report
  IDs, 8-way and 4-way hats with null state, array buttons, analog buttons,
  usages shared by two reports, element limit), error cases, and an
  integration test from descriptor bytes through `Mapper` to
  `GamepadState` with `b{hid:...}` and `a{hid:...}` inputs.
- Verified locally: fmt, clippy `-D warnings` (workspace, all targets),
  workspace tests, rustdoc `-D warnings`, wasm32 build, `cargo +1.85 check`
  (native).

## Decisions

- A separate crate rather than a module of `anygamepad`. Reason: firmware
  and other non-game consumers (airHID) need it without the facade's
  providers; it only needs the model.
- Lenient parsing: a stray `End Collection` or `Pop` is ignored, open
  collections are closed at the end, reserved items are skipped. Errors
  only for truncated items and the size and depth limits. Reason: a
  descriptor that works with an operating system should parse.
- A logical or physical maximum reads as unsigned when its minimum is not
  negative (`15 00 25 ff` is 0 to 255), as Linux does. Reason: many devices
  encode their ranges that way.
- `RawReader::new` keeps only the Joystick, Game Pad and Multi-axis
  Controller top-level collections when there are any. Reason: composite
  devices (keyboard or consumer keys next to the pad) would otherwise fill
  the layout with elements no gamepad profile uses.
- Elements are keyed by usage, and a usage reported by several fields is
  one element. Reason: profiles name elements by `RawSource`; Bluetooth
  pads report the same controls in more than one report.
- Vendor-defined pages and usage 0 are not elements. Reason: their meaning
  is device-specific, which is what protocol decoders (C7, C15) are for.

## Open questions

- Whether the parsed collections match Chromium's `HIDDevice.collections`
  for the same device in every detail (physical maxima of 0, items outside
  collections, delimiters). Needs a device read both ways (P1 reports with
  a descriptor).
- Whether this work should become a roadmap task (e.g. C16) in the next
  re-plan, as a blocker of C4-C7 and A3.

## Next steps

- Use it in the native providers (C4-C6) and in `anygamepad-report`
  validation (check that `collections` matches `descriptor` when both are
  present).
- Fixtures from real devices: airHID's USB capture firmware dumps report
  descriptors and timestamped reports of the owner's controllers.
