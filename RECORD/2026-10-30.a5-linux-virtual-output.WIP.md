# A5: Linux virtual output (uinput + UHID)

- Status: WIP
- Roadmap: ROADMAP/2026-10-14/ (task ID: A5)

## Goal

Present A4's emulated pads to Linux: uinput for an Xbox 360-style evdev
pad, UHID for exact HID emulation so the kernel's own drivers bind;
answer the feature and output reports those drivers send; udev rules.

## Done

- `anygamepad_virtual::uhid` (sans-IO): `struct uhid_event` encoding
  (`CREATE2` without phys or uniq, `INPUT2`, `GET_REPORT_REPLY`,
  `SET_REPORT_REPLY`, `DESTROY`) and parsing of the kernel's requests
  (`START`, `STOP`, `OPEN`, `CLOSE`, `OUTPUT`, `GET_REPORT`,
  `SET_REPORT`).
- `anygamepad_virtual::xbox360::evdev_events`: the events `xpad` sends
  for an input packet (keys, sticks with Y down, triggers, hat), and the
  capabilities (`EVDEV_KEYS`, `EVDEV_AXES` with `xpad`'s ranges).
- `anygamepad_virtual::linux::LinuxVirtualPad`: creates the pad (uinput
  with force feedback for the Xbox 360 Controller, UHID for the HID
  targets), sends the state on `update`, answers feature reads with the
  pad's replies (EIO for unknown reports), accepts feature writes, and
  returns the host's commands (rumble from uinput force feedback, rumble,
  light bar and player number from output reports).
- `examples/mirror.rs`: physical pad (C4, grabbed) mirrored as a chosen
  virtual pad, rumble sent back.
- `data/udev/70-anygamepad.rules` and `docs/linux-permissions.md`.
- `anygamepad::native::evdev::spec_mapping` takes the driver: `xpad`
  reports Xbox X (west) as `BTN_X`, which is `BTN_NORTH`'s code.
- Tests: UHID layout and parsing, the request answers, `xpad` events.

## Decisions

- UHID through a plain non-blocking file, uinput through the `evdev`
  crate; `nix` (already a dependency of `evdev`) sets non-blocking mode.
  Reason: no unsafe code in anygamepad.
- No phys or uniq on UHID pads. Reason: nothing that looks like a serial
  number or an address; the pairing feature report has the made-up one
  (A4).
- Virtual pads skipped by the mirror example by their sysfs path
  (`/devices/virtual/`). Reason: the provider would otherwise read back
  its own output.
- `xpad` X/Y: from research note 05, which lists `BTN_X` as west for
  `xpad`. To confirm on a device.

## Open questions

- Not run against a kernel: the container has neither `/dev/uinput` nor
  `/dev/uhid`. Whether `hid-playstation` accepts the virtual DualShock 4
  and DualSense (feature report IDs and sizes) is the main unknown.
- The Switch Pro set-up exchange is answered since C7 (USB commands,
  subcommand ACKs, SPI flash with the nominal calibration, device
  information); whether it satisfies `hid-nintendo` (which reads more
  of the flash and checks more replies) is untested.
