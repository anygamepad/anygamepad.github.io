# W2: Live tester on the core web backend

- Status: WIP
- Roadmap: ROADMAP/2026-10-10/ (task ID: W2)

## Goal

Live view of buttons and axes for every connected gamepad, driven by the
library's web provider (C11): the browser's `id` string and `mapping`, raw
values, the update rate, and a vibration test. Chromium, Firefox and Safari.

## Done

- Bindings (`anygamepad-wasm`): `DeviceInfo.canonical` (`CanonicalLayout`:
  the canonical button or axis of each raw index, standard mapping only,
  from `web::standard`), and `Gamepads.timestamp(device)`
  (`Gamepad.timestamp` at the last `update()`). TypeScript check and browser
  test extended.
- Web app (`apps/web`), one card per gamepad:
  - Header: name, `vvvv:pppp`, the mapping explained, button and axis
    counts, and `Gamepad.id` verbatim.
  - Update rate (`src/rate.ts`): changes of `Gamepad.timestamp` over the
    last second.
  - Controller drawing (`src/diagram.ts`, SVG), standard mapping only:
    canonical pressed buttons, trigger travel, stick positions (canonical
    Y up), each control titled with its canonical name.
  - Raw buttons (index, canonical name, value, pressed/touched, meter) and
    raw axes (index, canonical name, signed value, bar from the centre),
    for every gamepad (`src/live.ts`).
  - Vibration test: strong motor, weak motor, both, and triggers when the
    browser lists `trigger-rumble`; one second at full strength, then every
    motor stops. Buttons disabled, with a note, without an actuator.
- `src/tester.ts`: a sampler (every 4 ms, paused while the page is hidden)
  runs `update()`, hotplug and the rate meters; the frame loop draws.
- Styles for the above, light and dark, down to phone width (checked with
  screenshots at 1100 and 390 px).
- Smoke test (`tests/smoke.mjs`) now covers two fake gamepads (standard
  DualShock 4 with a recording vibration actuator, DragonRise pad without
  mapping or actuator): card facts, canonical names, rate > 0, raw values,
  drawing state, the vibration calls (including a test cut short by
  another), hotplug of one gamepad with the other card still live, and
  unplugging all. `BROWSER=chromium|firefox|webkit`.
- CI: new `web-smoke` matrix job runs the smoke test on the built site in
  Playwright's Firefox and WebKit; `deploy` waits for it.
- Sizes (gzip): wasm 74.2 KiB, JS 34.9 KiB, CSS 1.3 KiB (W1: 73.3, 32.4,
  0.6).
- Found by review and fixed before commit: a vibration test started during
  another stopped only its own motors, so the provider kept refreshing the
  other effect. The smoke test fails without the fix.
- Verified locally: fmt, clippy (native, wasm32, feature sets), native
  tests, wasm browser tests in Chrome, `.d.ts` check, MSRV 1.85 check, web
  check/build/size, smoke test in Chromium 141.

## Decisions

- Two loops: a 4 ms sampler for `update()` and the rate, the frame loop for
  drawing. Reason: a rate measured once per frame caps at the display's
  refresh rate (60 Hz hides a 250 Hz gamepad), and hotplug does not need to
  wait for a frame.
- The rate counts changes of `Gamepad.timestamp`, read with
  `Gamepads.timestamp()`. Reason: the timestamp changes when the browser
  gets new data, even when values stay equal; `timestamp()` avoids
  serializing a snapshot 250 times a second. It is the rate the page sees,
  capped by the browser's own polling and the 4 ms timer, not the device's
  report rate (that is W3, WebHID).
- jq79 renders the card skeleton; the live part is built with the DOM API
  and updated per frame outside jq79's reactivity, touching only changed
  cells. Reason: per-frame values in the reactive store would re-render
  the template every frame (ADR 0005: no reactivity per frame). The live
  view re-attaches when jq79 renders a card anew (tested by unplugging the
  other gamepad).
- Meters and bars are driven by one custom property, `--value`, through
  `transform: scaleX()`; an axis bar spans the right half and a negative
  value mirrors it to the left. Reason: no layout per frame, and one
  property per element.
- The canonical layout comes from the library (`DeviceInfo.canonical`),
  not from a table in TypeScript. Reason: `web::standard` stays the only
  copy of the W3C standard mapping.
- The drawing is shown for the standard mapping only, with canonical names
  rather than brand glyphs (A/B/X/Y, cross/circle/...). Reason: other
  mappings need profiles (D4) and the mapping engine (W5); glyphs need
  device identification per brand.
- Gamepads are opened with shared access when they appear. Reason: polling
  and the vibration test need an open device; shared access leaves them to
  other consumers.
- Firefox and WebKit run in CI from Playwright's builds, not on this
  machine. Reason: the container has only Chromium and must not run
  `playwright install`. WebKit on Linux stands in for Safari's engine; it
  is not Safari.

## Open questions

- Nothing has been tried with real gamepads (none here): update rates,
  vibration on real Chrome/Edge, Firefox (vibration support unconfirmed),
  Safari on macOS and iOS. Owner check wanted.
- Touchpad, motion sensors and battery are outside the standard Gamepad
  API; they come with WebHID (W3) and the protocol drivers (C7).
