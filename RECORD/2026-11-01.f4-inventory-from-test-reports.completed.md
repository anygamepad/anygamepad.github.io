# F4: Lab inventory from test reports

- Status: completed
- Roadmap: ROADMAP/2026-11-01/ (task ID: F4)

## Goal

The owner tests the collection first and lists it later (2026-11-01): the
test modes name a unit the inventory lacks, the test reports carry its
code, and a tool builds `data/lab/inventory.toml` from the reports.

## Done

- Catalog: an optional `short` name per model (2 to 8 uppercase letters
  and digits), set for the 9 named models (`DS5`, `DS5E`, `DS4`, `DS3`,
  `NSP`, `X360`, `XSX`); generic models have none. Schema and README.
- `anygamepad_db::lab::propose_code(model, used)`: the short name and the
  next number free among the codes this machine knows (`DS5-03`), `PAD`
  without a short name; doctest.
- `anygamepad_report::test_report::add_units(inventory, reports)` and
  `InventoryUpdate` (units added, conflicting codes left out); test.
- `cargo run -p anygamepad-report --features json --example inventory --
  <folder> data/lab/inventory.toml`: reads the test reports of a folder
  (other files are skipped, with the reason), appends the new `[[unit]]`
  tables to the file (comments, notes and machines stay as written),
  checks that the result reads back valid, and prints what it added and
  any conflict. `data/lab/README.md` says how.
- Web test mode (`anygamepad-wasm-testing`: `proposeUnitCode`,
  `isUnitCode`): the unit is a text field with the codes this browser
  knows (inventory, saved reports) and "New unit: <code>"; a model with
  no known unit gets the proposed code; an invalid code is refused.
- Desktop Test page: the same (field, "Known" codes, "New unit"); test.
- Detection no longer counts the unit (`Configuration::detection_differs`
  compares model, mode, kind and transport). Before, naming a unit other
  than the inventory's first failed the detection step; test.
- Web smoke test: the Xbox 360 pad gets `X360-01`, a bad code is refused,
  the report and its file name carry the code, and the next proposal
  after saving is `X360-02`.
- Checked: fmt, clippy (workspace; per crate with all features; wasm32;
  the desktop for macOS and Windows), tests, Rust 1.85, `tsc` of both
  modules' declarations, the web build (tester 155.5 KiB, test mode 162.3
  KiB), both smoke tests in Chromium.

## Decisions

- Codes follow the usual asset-tag pattern, a type prefix and a number
  (`DS5-03`). Reason: short enough for a label on the pad, readable, and
  numbered per type; the owner asked whether it is a usual convention
  (2026-11-01): it is a common pattern, not a standard, and only a
  proposal (any code of the format works).
- Two models may share a short name (`DS4` for both DualShock 4 versions,
  `X360` for the wired and wireless pads). Reason: people name them so;
  the numbers stay unique across both, since every known code counts.
- The tool appends to the file instead of rewriting it. Reason: a
  hand-edited inventory keeps its comments and order.
- The tool is an example of `anygamepad-report`, not a new crate. Reason:
  it needs the test report format and the inventory format, both there;
  no binary to ship.
- The default unit for a model this machine knows is the one picked last,
  not a new one. Reason: the same pad is usually tested in its other
  modes next; "New unit" is one click.

## Open questions

- Machines are not in the reports, so the inventory's machines stay
  hand-written (or absent).
- The unit picked last is kept per browser (localStorage) and, on the
  desktop, while the app runs.
