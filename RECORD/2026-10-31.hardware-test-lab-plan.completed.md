# Hardware test lab plan: a test mode in every app

- Status: completed
- Roadmap: ROADMAP/2026-10-31/ (task IDs: H1-H9, F4, M6; re-plan of C4,
  C7, C8, C15, D3, P4, W3, A1, A2, A3, A5, A11)

## Goal

Owner request (2026-10-31): a robust, comfortable and extensible way to
test real controllers. Every app (web, desktop on Linux, later Windows and
macOS) gets a test mode in which the person picks the controller or the
kind of controller to test, and that writes a report file (a download on
the web). The owner collects controllers (several DualSense, Xbox Series,
DualShock 4, DualShock 3, 8BitDo, GuliKit, GameSir and other brands) and
tests on Windows, Linux and macOS.

## Decisions

- A new dated roadmap version rather than an in-place edit. Reason: a
  re-plan on a later day than the version's (AGENTS.md).
- Tasks with merged code that were never tried on hardware (C15, W3, C4,
  C7, A1, A2, A3, A5, A11) are in progress (`active`, blue), with what is
  left as their duration, closed by the first test campaign (H6). Reason:
  their "Done when" needs real pads; the test mode makes those checks
  repeatable and leaves evidence. Remaining days: C15 2, W3 2, C4 3, C7 7
  (adaptive triggers, DualSense Bluetooth light bar set-up, Switch Pro over
  WebHID), A1 2, A2 2, A3 5 (wizard in the desktop app), A5 3, A11 3.
- Task prefix `H` (hardware testing). Reason: `T1` would read like the
  baseline milestone `t0`.
- A test report is its own format that embeds a device report (ADR 0008).
  Reason: device reports must fit an issue body and are meant for anyone;
  test evidence is large and comes from a lab.
- A controller catalog separate from device profiles. Reason: a model as
  sold, with its modes and how to switch them, is not a mapping of one
  identity; a model points to the profiles of its modes.
- One runner in the library, plans as data. Reason: the wizard's shared
  state machine already works on the web and the desktop; new checks and
  controllers must not need work in each app.
- F4 keeps its ID, now the inventory in H2's format (3 days, after H2).
  Reason: same purpose; IDs stay stable.
- D3 waits for H6, C8 for H9, P4 for H1. Reason: profiles verified by
  test reports, mode detection from identities with ground truth, and
  curation of test reports.
- Corrections: D4 and M1 dated 2026-10-25 (their RECORDs), W5-W7 bars
  from their RECORD dates.
- Result: M6 2026-12-12, M5 2027-01-01, M3 2027-01-29, M4 2027-02-03
  (2027-01-09 in the 2026-10-14 version, not recomputed since
  2026-10-25). Critical path H2 -> H3 -> H4/H5 -> H6 -> C4 -> D3 -> C8 ->
  C10 -> A10 -> M4. Computed with a scratch script (not committed): end =
  start + days, start = latest blocker end or the baseline, slack against
  M4.
