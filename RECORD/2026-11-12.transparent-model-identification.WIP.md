# Transparent model identification in the test mode

- Status: WIP (planned; nothing implemented yet)
- Roadmap: ROADMAP/2026-11-11/ (follow-up of H10 and H4; no new task ID,
  no date moves; status note in place)

## Goal

Owner request of 2026-11-12: identifying the hardware model must be
transparent to the person, meaning it happens without them doing anything.
After PAD-01's first session
(`RECORD/2026-11-12.test-mode-feedback-pad01.completed.md`) the test page
still asks them to click "Connect it with WebHID", then "Check the
firmware", to pick USB or Bluetooth, and to confirm the model. The owner
agreed to the adjustments below on 2026-11-12.

## Decisions

The agreed adjustments, for the web test page (`apps/web/src/test-mode.ts`,
`apps/web/src/tester.ts`, `apps/web/src/App.html`):

1. **The best identity wins, always.** When a pad shows through the
   Gamepad API and WebHID, detection uses the WebHID identity (USB IDs),
   so the person never sees the generic model when the exact one is
   known. Today this happens only when WebHID is connected from the list
   or the detected stage (`TestMode.upgradeToHid`). Extend it to every
   stage before the session starts (connect, waiting, check, plan), and
   pair a Gamepad API pad with its WebHID twin when the IDs are hidden
   (macOS): same family and product name, connected at the same time.
2. **Pads granted before reopen without a dialog.** `WebHid` already
   adds the devices of `navigator.hid.getDevices()` at start
   (`crates/anygamepad/src/web/hid.rs`, around line 316), and `added()`
   then detects them once open. Check that the exact model shows on a
   reload without any click, and make the list stage say so ("connected
   through WebHID before: detected by itself").
3. **Firmware read without asking when it changes nothing.** Over USB, and
   over Bluetooth when the pad already sends its full report (macOS's
   GameController switches the DualSense itself). The report form is in
   `HidPoll.input.form` (`ReportForm`: `usb`, `bluetooth_reduced`,
   `bluetooth_full`, `crates/anygamepad-wasm/src/hid_devices.rs`); expose
   it to the test mode (`TestPad`), and call `checkFirmware()` by itself
   in those cases. Ask only for a Bluetooth pad in its reduced report.
4. **No transport question when WebHID tells.** WebHID gives it from the
   report sizes (`HidDeviceInfo.transport`); the Gamepad API does not,
   and keeps asking.
5. **No "Confirm" step when there is no doubt.** When the USB IDs match
   one catalog model and mode (a single candidate with `specificity` > 0)
   and the firmware answered as Sony's pads do (or the model has no
   firmware check), go straight to the plans, with the unit proposed. Keep
   "Confirm" when there are several candidates, a generic model, a
   transport to ask, or a firmware that did not answer.

Limits that stay, as agreed:

- The first WebHID permission takes one click and the browser's chooser,
  once per pad (browser security). Make that one button prominent.
- On Bluetooth in the reduced report, reading the firmware switches the
  pad to its full report until it is turned off, and other programs may
  then not read it: the page asks once. The Full plan's touchpad and
  motion steps need the full report anyway, so it can be one question at
  the start: "Switch it to its full report? (needed for touchpad and
  motion)".
- Safari and Firefox have no WebHID: there the exact model of a pad that
  hides its IDs (macOS) stays unknown, and the person picks it.

## Open questions

- Pairing a Gamepad API pad with its WebHID twin when the IDs are hidden
  (item 1): name and family may not be enough with two pads of one model
  connected; the test mode can then ask which one, by a button press.
- Whether skipping "Confirm" (item 5) should still show the unit code
  before the plans, so the person can change it.
