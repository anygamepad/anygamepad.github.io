# P1: Device report schema

- Status: completed
- Roadmap: ROADMAP/2026-10-14/ (task ID: P1; re-planned the same day, see
  `RECORD/2026-10-14.adr-0007-local-first-reports.completed.md`)

## Goal

The device report format of the collection pipeline: one Rust crate
(`anygamepad-report`) that the web app (in WASM), the desktop app and the
tools use to build, scrub, validate, read and write reports, a generated
JSON Schema, and no personal data by construction.

## Done

- `anygamepad-report`: `Report` (`format`, `schema_version`, `created`,
  `source`, `host`, `user`, `views`), `Source` (`App`, versions), `Host`
  (OS, OS release from the desktop, browser), `UserStatement` (product in
  the person's words, `ControllerMode`), `View` (identity, fingerprint,
  family, profile, `RawLayout`, outputs, capabilities, `HidData`, confirmed
  `Mapping`), `HidData` (descriptor, collections, input samples;
  `sample()` keeps the first report of each ID and length), `HexBytes`,
  `Date`, `Version`. `Report::new`, `View::new` (fingerprint and family
  from the identity).
- `privacy`: `Report::scrub` replaces hexadecimal identifiers (12 or more
  digits, joined by `:` or `-`: Bluetooth addresses, serial numbers, UUIDs)
  and email addresses with `[redacted]`, turns control characters into
  spaces, trims, cuts long texts, drops Nintendo `0x21`/`0x81` input
  samples, recomputes fingerprints of changed identities, and returns the
  `Redaction`s (field path and finding) for the preview.
- `Report::validate`: format and version, 1 to 8 views, web reports with a
  browser and web views only (desktop the reverse), every view of the
  host's OS and browser, fingerprints and descriptor hashes that match,
  texts without findings, size limits (texts, layouts, samples, descriptor,
  HID nesting and entries), finite axis ranges, confirmed mappings valid and
  without `when`.
- Feature `json`: `from_json` (compact or indented; compact form at most
  60,000 bytes, text at most four times that), `to_json` (compact, what an
  issue carries), `to_json_pretty` (files, display). Unknown fields are
  errors at every level the crate defines.
- Feature `schemars`: `json_schema()` with `$id`
  `https://anygamepad.github.io/schema/report.json`, committed as
  `data/reports/schema.json`; the web build publishes it at
  `/schema/report.json` (the Vite plugin now emits both schemas).
- `anygamepad-db`: `Mapping::validate` and `InvalidMapping`, for mappings
  outside a profile; profile error messages unchanged.
- `data/reports/README.md` (format reference, privacy rules, limits, a
  small example that the tests validate) and `data/reports/example.json`
  (illustrative DualSense over USB in Chrome on Windows, Gamepad API and
  WebHID views; generated by the tests).
- Tests: unit tests (dates, versions, hex bytes, samples, identifier
  detection, scrubbing); `tests/report.rs` (every validation rule, scrub
  redactions and fingerprints, identifying samples); `tests/schema.rs`
  (schema and example up to date with `UPDATE_SCHEMA=1`, round trips in
  both forms, README example, the schema rejects what the types reject,
  size limits).
- CI: clippy and tests of `anygamepad-report` with all features, wasm32
  clippy, MSRV check.
- Sizes: the example report is 9,087 bytes compact (23,456 indented); a
  desktop report with the DualSense's descriptor and HID structure in three
  views and a confirmed mapping in each is 25,688 bytes compact.
- Verified locally: fmt; clippy with `-D warnings` (workspace native and
  wasm32, `anygamepad-report` with all features native and wasm32);
  workspace tests and `anygamepad-report`/`anygamepad-db` with all
  features; rustdoc with `-D warnings` (all features, as for
  `anygamepad-db`); `cargo +1.85` checks (native, wasm32, all features)
  and the crate's tests; the web build (both schemas in `dist/schema/`,
  wasm 85.6 KiB gzip, unchanged) and its smoke test in Chromium.

## Decisions

- The confirmed mapping is `anygamepad_db::Mapping` with inputs naming the
  view's raw elements. Reason: P4 turns it into a profile without
  translation, and the wizard (W4) speaks the same terms.
- Reports carry the day (UTC), not a time, and no report ID. Reason: the
  day tells which versions were current and correlates less; stores key
  reports themselves and the server hashes the content (ADR 0007).
- The size limit applies to the compact JSON (60,000 bytes). Reason: an
  issue body holds 65,536 characters; the indented form is about two and a
  half times as long, and the HID structure is most of a report.
- `scrub` rewrites texts and recomputes the fingerprint instead of keeping
  the device's live fingerprint. Reason: a fingerprint over a name with an
  address in it identifies one device; the redacted one groups all of them.
- Scrubbing is a heuristic on top of identities that have no serial or
  address fields. Reason: names a person gave a device cannot be told from
  product names; the preview before sharing (W6, A3) shows every text.
- `host.browser` for web reports, `host.os_version` documented as desktop
  only but not rejected on the web. Reason: a browser may give it later
  (client hints); nothing in it identifies a person.
- The WASM bindings and TypeScript types of reports come with W6. Reason:
  W6 is their first caller, and exported functions grow the `.wasm` bundle
  even unused; the crate itself builds for wasm32 and is checked in CI.
- `deny_unknown_fields` on every struct of this crate. Reason: data the
  format does not know must not ride along to a store or an issue. The
  model's types (identity, layout, HID) accept and drop unknown fields;
  a reader that re-serializes stores none of them.

## Open questions

- Whether macOS or Windows show the name a person gave a Bluetooth device
  as the product name through some APIs (GameController, Windows.Gaming.
  Input). C6 and C5 should check; the preview covers it meanwhile.
- More input reports that answer identity requests (other vendors' command
  replies) will show up with real devices; extend the list in `privacy`.
