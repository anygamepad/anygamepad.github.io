# C3: Mapping engine

- Status: completed
- Roadmap: ROADMAP/2026-10-14/ (task ID: C3; dates of C9, D4, W5 and M1
  updated)

## Goal

Apply a device profile's mapping (D1) to the raw elements a provider reads,
producing the canonical state: button remap, axis inversion and range,
combined axes, hat-to-dpad, dead zones. Pure and deterministic, so it is
unit-tested natively and runs unchanged in WebAssembly.

## Done

- `anygamepad::mapping`: `Mapper::new(&Mapping, &RawLayout)` resolves every
  input against the layout once; `Mapper::apply(&RawState, &mut
  GamepadState)` maps each poll without allocating: buttons, sticks,
  triggers, halves, hats and deadzones. It copies touches and power and
  keeps the latest motion sample. `capabilities()` gives the controls the
  mapping drives plus the layout's sensors, touchpads and battery;
  `unresolved()` gives the inputs the layout lacks, with their target.
- `PRESS_THRESHOLD` (30/255) moved from `web::standard` to `mapping`;
  `web::standard` re-exports it.
- Format documentation (`Mapping` docs, so the regenerated `schema.json`,
  and `data/profiles/README.md`): the threshold, halves adding up, deadzone
  rescaling and the two defaults below.
- Unit tests: ranges (also reversed), symmetric axes read exactly, combined
  trigger axis, inverted halves, halves adding up, hats to d-pad and stick,
  axes to buttons, buttons to axes, deadzones, canonical sources and their
  override, derived trigger buttons, unresolved inputs and capabilities,
  NaN, infinite and missing values, touches, power and motion.
- Integration tests (`crates/anygamepad/tests/mapping.rs`): the curated
  standard profile gives exactly what `web::standard::map` gives on 2,000
  generated states (NaN, infinities, out of range, threshold edges); real
  SDL GameControllerDB entries (Afterglow Xbox 360 on Linux, Cyborg V.3
  combined triggers, Mad Catz digital triggers, 8BitDo N64 C buttons as
  stick halves, Gravis Destroyer Tilt hat stick and axis d-pad, Ipega half
  axes); every one of the 2,279 entries resolves against a layout of its
  size.

## Decisions

- The engine lives in `anygamepad` (`anygamepad::mapping`), not in
  `anygamepad-db`. Reason: the database crate describes profiles; turning
  provider data into canonical state belongs next to `provider` and
  `protocol`. Tools that need it (P4) can use `anygamepad` without default
  features.
- Inputs name raw elements by `RawSource` equality, not by position.
  Reason: the layout says what each element is; `b3` is the element the
  provider lists as `Index(3)`, which index-based backends list in order.
- Resolve once, map many: `Mapper` keeps indices into the raw state.
  Reason: no lookups or allocations in the frame loop.
- Whole stick axes are `(2v - (min + max)) / (max - min)`, not `2t - 1`.
  Reason: symmetric ranges (Gamepad API) then read exactly as themselves,
  so the standard profile matches `web::standard::map` value for value.
- A deadzone rescales the travel beyond it. Reason: no jump at its edge,
  full range kept. It is per axis, as in the format; radial stick deadzones
  are for games (C9 may offer helpers).
- Trigger buttons follow their axis from 30/255 unless the mapping sets
  them. Reason: SDL GameControllerDB maps triggers as axes only, while the
  model has digital trigger buttons. This answers D1's open question. The
  reverse (an analog axis from a digital trigger button) is not derived: a
  pad without analog triggers does not get them.
- Raw elements with canonical sources (`RawSource::Button`, `Axis`) drive
  their own control unless the mapping sets it. Reason: XInput and gilrs
  need no profile (C2's single path), and a profile can still fix a pad.
- Inputs the layout lacks are reported, not errors. Reason: one profile
  covers several layouts (OS, transport); W5 and P4 can show the mismatch.
- NaN reads as rest, infinities clamp, an axis with an empty range is
  unresolved. Reason: a bad raw value must not reach the game.
- `web::standard::map` stays. Reason: it also maps the extra buttons
  browsers append, which need device profiles; D4 and W5 replace it.
- The mapper's capabilities have no outputs. Reason: outputs come from the
  provider (`DeviceInfo::outputs`), not from a mapping.

## Open questions

- Per-device calibration (centre offset, measured range) is not in the
  format: the centre is the middle of the layout's range, so a 0-255 axis
  resting at 128 reads 0.004. D3 will show whether profiles need more than
  a deadzone.
- Unsetting a target in a later mapping entry (D1's open question) is
  still not possible.
