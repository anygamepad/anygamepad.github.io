# DualSense controller information and the tester's new layout

- Status: completed
- Roadmap: ROADMAP/2026-11-11/ (task IDs: C7, W3; web app polish outside
  the plan)

## Goal

The owner asked on 2026-11-12, in one session:

1. Show what `ds.daidr.me` reads from a DualSense over Bluetooth (factory
   information, diagnostics, press counts, stick travel).
2. Tabs for dedicated views of the activity log and the test mode, instead
   of the activity box in the side column and the footer link.
3. The theme switch and the settings button in the footer.
4. The pads in a row, the selected pad's detail full width, with the
   controller information beside the drawing.
5. Vibration: a level per motor, a pattern selector, and a mode where two
   buttons of the pad play the level and pattern (one strong, one weak).
6. A colour picker for the light bar.
7. The sharp points at the bottom of the DualSense drawing's grips.

## Done

- Library: `protocol::playstation::info`: `InfoReader`, sans-IO. Reads the
  firmware information, feature report `0x22` (Bluetooth patch), and
  test commands through `0x80`/`0x81` (56-byte pages, 1 s timeout per
  command, CRC-32 with prefix `0x53` on Bluetooth): serial number (reduced
  at once to board revision and colour), trigger motor models, touchpad
  firmware (USB only), battery voltage, usage block (`0x70`/1, open-ended
  pages; full layout only above update version 1106, 374 on the Edge,
  else the time in use). `Stat`, `Colour`, `ControllerInfo`. Gates from
  daidr's tester: retail firmware types 2 and 3, hardware ≥ 777 and
  firmware ≥ 65655 for the serial and patch, hardware ≥ 777 for the
  motors. Firmware info gains type, series, SBL, DSP and MCU DSP versions.
  10 tests against a simulated pad (USB, Bluetooth, old firmware, silent
  pad, failures, descriptor size, Edge layout, no identifier in the
  output).
- `anygamepad-wasm-testing`: `ControllerReader` (the page moves the
  bytes). In that module, not the tester's: the tester's grew from 155.2
  to 163.9 KiB with it, over its 160 KiB budget; the test mode's is now
  173.7 of 176.
- Web app:
  - Tabs Tester, Activity (`/#activity`) and Test mode (`/test/`),
    switched in place with `history.pushState`; the test mode's module
    loads when its tab first shows. Off its tab the test mode only runs a
    session already started; it does not detect pads.
  - Activity tab: counts and the newest 200 events (inputs on request),
    refreshed every 500 ms, and the download.
  - Footer: environment, privacy link, theme switch, settings.
  - Pads and the WebHID box in a row; the detail full width; "This
    controller" beside the drawing: what the browser tells, and for WebHID
    PlayStation pads "Read the controller info" (Bluetooth warning;
    calibration read first so motion comes calibrated) with Firmware,
    Hardware, Use, Connections and battery, Presses and Sticks groups.
  - Vibration (`src/vibration.ts`): levels per motor (and the trigger
    motors), seven patterns, Stop, and "Play from the pad" with a button
    per motor (default L1 strong, R1 weak); a press plays one cycle,
    holding repeats it.
  - Lights: a colour picker (writes at most every 50 ms) and Off/1-4 player
    LEDs.
  - DualSense drawing: the grip outline's segments now meet with matching
    tangents.
- Tests: the smoke tests cover levels, patterns, the trigger motors, the
  pad buttons (held and released), the colour picker, the controller
  information against the fake DualSense (`fakes.mjs` answers the test
  commands), the activity tab, and the test mode tab. Checked: fmt,
  clippy (workspace, wasm32), rustdoc, workspace tests, `tsc`, both smoke
  tests in Chromium (the main one three times). Firefox and WebKit run in
  CI. Screenshots looked at.
- JS budget 88 → 96 KiB: 90.4 KiB with these features.

## Decisions

- Research note 09 said never to send `0x80` commands; the owner's
  request reverses that for a fixed list of read-only commands. Reason:
  the information is useful (board revision, firmware, wear) and the
  forbidden parts can be left out. Never sent: Bluetooth address, PCBA
  and MCU unique IDs, battery and motor barcodes, assembled parts, the
  audio test commands. The serial number command is sent because the
  board revision and colour are coded in it: two characters are kept,
  the buffer is zeroed. The usage block and trigger answers carry serial
  numbers too: those bytes are skipped.
- Usage counters are shown, never logged or saved. Reason: together they
  can recognize a unit. The activity log keeps the firmware, board,
  colour, motor model and touchpad firmware (the model's facts) and the
  number of counters.
- Reading is a click, never automatic. Reason: over Bluetooth any feature
  report switches the pad to its full report for every application.
- Pad-button vibration listens on the selected pad only, on the Tester
  tab. Reason: buttons of other pads, or of a test session, must not
  start motors.
- Tabs keep `/test/` as a real page. Reason: links and the sync smoke
  test use it, and GitHub Pages serves it.
- The sync server still gets `page: "tester"` or `"test"` (the page
  loaded). Reason: its schema has no `activity`; the activity tab is the
  tester's page.
