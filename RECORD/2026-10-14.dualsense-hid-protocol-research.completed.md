# DualSense HID protocol research (daidr/dualsense-tester)

- Status: completed
- Roadmap: ROADMAP/2026-10-10/ (task IDs: C7, W3; addendum to F2)

## Goal

The owner pointed at `daidr/dualsense-tester` as a way to understand the
DualSense. Capture what it teaches about the protocol for C7 (protocol
drivers) and W3 (WebHID raw mode).

## Done

- `docs/research/09-dualsense-hid-protocol.md`, from the tester at
  `62dce17` (MIT): device IDs, transport from WebHID report sizes, input
  report offsets (USB and Bluetooth), button bits, touch, battery, the
  Bluetooth audio payload type in report `0x31`, output report layout, CRC32
  prefixes, feature reports (`0x20` firmware info, `0x80`/`0x81` factory
  test commands).
- Research index updated.

## Decisions

- Keep the protocol facts, not the code. Reason: our drivers are Rust and
  sans-IO (C7); the MIT license would allow reuse, but the TypeScript is
  tied to Vue and WebHID.
- Never send the `0x80` factory test commands. Reason: the tester uses them
  to read serial numbers, the Bluetooth MAC and other unique IDs, which
  AGENTS.md forbids collecting.

## Open questions

- First report from a real device: the owner's DualSense does not appear in
  the live tester (W2) in Chrome on macOS; `navigator.getGamepads()` returns
  `[null, null, null, null]`, so the browser exposes no gamepad and the
  tester's code is not at fault. The same pad works natively in
  `germadev/motorust` through GameController.framework. Likely cause
  (note 06, "DualSense in Chrome on macOS"): macOS switches the DualSense to
  its extended report, so IOKit HID readers such as Chrome get no input.
  Not yet checked: Safari, and the connection type.
- Which Bluetooth feature-set CRC prefix each pad accepts (`0x53` in the
  tester's DualSense code, `0xA3` in its DualShock 4 code).
- Everything in the note is unverified on a device.
