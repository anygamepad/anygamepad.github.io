# C11: Web backend and JS bindings

- Status: WIP
- Roadmap: ROADMAP/2026-10-10/ (task ID: C11)

## Goal

Run the library in the browser: a web provider for `wasm32-unknown-unknown`
(Gamepad API, WebHID opt-in) implementing the `Provider` trait (C2), and the
`anygamepad-wasm` bindings with generated TypeScript types that the web app
(W2, W3) is built on.

## Done

Part 1, Gamepad API (enough for W2):

- `anygamepad-model`: `tsify` feature. `derive(Tsify)` on every serde
  struct/enum; hand-written TypeScript for the types with hand-written serde
  (`named_enum!` and `enum_set!` unions, `Button`, 64-bit hashes,
  `SdlGuid`) through a `ts_decl!` macro. `GamepadState.axes` is now an
  object keyed by axis name in human-readable formats, clamped when read.
- `anygamepad::web` (feature `web`, default):
  - `detect(user_agent, max_touch_points)`: browser engine, major version
    and OS.
  - `standard`: W3C standard layout to canonical state and capabilities.
  - `WebProvider`: `Provider` over a `GamepadSource`; hotplug by slot,
    reconnection and layout changes as new devices, `snapshot()` with the
    verbatim Gamepad API values, rumble and trigger rumble through
    `vibrationActuator`.
  - `sys` (wasm32): `BrowserGamepads` source on web-sys, with our own
    externs for `vibrationActuator`, `id` and `mapping`.
- `anygamepad-wasm`: `Gamepads` class (`update`, `devices`, `info`, `open`,
  `close`, `poll`, `state`, `snapshot`, `send`, `environment`); typed
  `.d.ts`; `ts/check.ts` + `ts/tsconfig.json` type-check it.
- Tests: provider logic, user agent table and standard mapping natively
  (fake source); browser tests for the glue and the JavaScript value shapes;
  model serde tests for the new axes form.
- CI: clippy of `anygamepad` without default features, wasm32 MSRV check,
  TypeScript check of the generated `.d.ts` (TypeScript 6.0.3, Node 22).
- Verified locally: fmt, clippy (native, all features, wasm32), tests,
  browser tests in headless Chromium 141, rustdoc with `-D warnings`,
  `cargo +1.85` checks, `tsc` on the generated `.d.ts`. Firefox runs in CI
  only.

## Decisions

- Raw elements are the Gamepad API lists verbatim (`RawSource::Index`), also
  for `"standard"` devices. Reason: browsers remap differently, reports need
  what the browser said, and the standard layout's Y sign is the opposite of
  the canonical one; `RawSource::Index` already names the Gamepad API.
- The standard layout is converted by a fixed table in `web::standard`:
  Y inverted, buttons 6/7 also give the trigger axes, pressed from 30/255
  (Chromium's analog threshold, XInput's trigger threshold), buttons from
  17 on become extra buttons (Chromium appends the touchpad click, capture
  or share button there). Reason: W2 needs a canonical view before C3/D4;
  C3 may turn the table into a built-in profile.
- `WebProvider` holds a `Box<dyn GamepadSource>`; the browser source exists
  on wasm32 only and `WebProvider::new()` fails with `Unsupported`
  elsewhere. Reason: headless browsers have no gamepads, so the provider
  logic is tested natively with a fake source; games can call `new()` on
  every target.
- `web` is a default feature whose dependencies are wasm32-only optional
  dependencies. Reason: Cargo cannot enable a feature per target; this is
  the closest to ADR 0002's "automatic on wasm32", and
  `default-features = false` removes it.
- Reconnections between two frames are detected by counting
  `gamepaddisconnected` events per slot. Reason: browsers can show a new pad
  in `getGamepads()` before its `gamepadconnected` event, which a connection
  counter would report as a reconnection.
- Rumble plays 5 s effects (Chromium's maximum) replayed every 4 s while
  non-zero; zero calls `reset()`; a trigger rumble effect also carries the
  body motors (a new effect replaces the playing one). Reason: the model's
  outputs are continuous; a hidden tab (no frames) stops within 5 s.
  `Access::Exclusive` is `Unsupported` (a page cannot hide a pad).
- Own `wasm-bindgen` externs for `vibrationActuator`, `Gamepad.id` (kept as
  a JS string, compared without copying each frame) and `Gamepad.mapping`
  (verbatim). Reason: no crate-wide `web_sys_unstable_apis` (research 06).
- The bindings convert with `serde_wasm_bindgen::to_value` (defaults:
  `None` is `undefined`, matching tsify's `T | undefined`) and declare the
  result types with `unchecked_return_type`; tsify only generates the
  declarations. Reason: errors stay ordinary `Result`s (tsify's
  `into_wasm_abi` is deprecated for leaking on errors).
- `GamepadState.axes` is serialized as a struct, not a map. Reason:
  serde-wasm-bindgen turns maps into JavaScript `Map`s.
- `codegen-units = 1` for `anygamepad-model` in the dev and release
  profiles. Reason: the linker drops object files the bindings do not
  reference, with their TypeScript custom sections (`TouchPoint`,
  `TouchpadInfo`, `Capabilities` were missing); the CI `tsc` check catches
  a regression.
- The access mode crosses the boundary as a string typed `Access`
  (`"shared" | "observe_only"`). Reason: `wasm-bindgen` string enums add an
  undocumented hidden variant that fails `missing_docs`.
- Device ids are `u32` in JavaScript. Reason: the web provider counts them
  up from 1.

## Open questions

- No real gamepad was available: behaviour on real devices in Chromium,
  Firefox and Safari is unverified until W2.
- Firefox has no `vibrationActuator` (only `hapticActuators` behind a
  pref), so no rumble there.
- `Gamepad.touches` (Firefox) and motion are not read.
- WebHID exposes parsed collections, not the raw report descriptor, so a
  web `DescriptorHash` cannot equal the native one; decide in part 2 how
  web reports identify descriptors.
- W1 must type-check with the `esnext.disposable` lib: `wasm-bindgen`
  declares `[Symbol.dispose]` on classes.
