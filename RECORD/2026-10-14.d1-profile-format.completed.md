# D1: Device profile format and JSON Schema

- Status: completed
- Roadmap: ROADMAP/2026-10-14/ (task ID: D1; status of W8 updated too)

## Goal

The profile format of ADR 0003: Rust types as the single source of truth,
TOML files in `data/profiles/`, a generated JSON Schema, and the rules that
pick a profile for a device and merge its mapping.

## Done

- `anygamepad-db`: `Profile` (`schema_version`, `name`, `source`,
  `verified`, `family`, `face`, `indices`, `attribution`, `[[match]]`,
  `[[mapping]]`), `MatchRule`, `Mapping` (`when`, `buttons`, `axes`),
  `AxisMapping` (an input string, or a table with `input` or
  `negative`/`positive`, plus `deadzone`), `Input` (SDL-style strings:
  `b3`, `+a1~`, `h0.4`, `b{evdev:0x0130}`), `validate`, `match_score`,
  `best_match`, `mapping_for`, `face_layout`.
- Features: `toml` (`from_toml` validates, `to_toml` writes IDs as
  `0x054c`) and `schemars` (`json_schema`, with `$id`
  `https://anygamepad.github.io/schema/profile.json`).
- `RawSource` has a text form in the model (`3`, `evdev:0x0130`,
  `hid:0x0001:0x0030`, `button:south`, `axis:left_stick_x`).
- `data/profiles/schema.json` is generated by a test (`UPDATE_SCHEMA=1`)
  that fails when stale (CRLF tolerated for Windows checkouts). Hand-written
  schema parts (inputs, axis tables, map keys via `propertyNames`) are
  tested against invalid documents with `jsonschema` (dev-dependency).
- Every `data/profiles/*.toml` and the README example parse, validate,
  pass the schema and survive a `to_toml` round trip.
- First curated profile: `gamepad-api-standard.toml` (W3C standard layout,
  mirrors `anygamepad::web::standard`).
- The web build publishes the schema at `/schema/profile.json` (Vite
  plugin in `apps/web/vite.config.ts`).
- Format reference: `data/profiles/README.md`.
- CI: clippy and tests of `anygamepad-db` with all features, wasm32 clippy,
  MSRV check. The `.wasm` bundle did not grow (85.6 KiB gzip).
- Roadmap 2026-10-14 status updated in place: W8 (finished in #7 but not
  marked), D1 and D2 done; dates recomputed (10 days earlier: M1
  2026-11-10, M2 2026-11-25, M4 2027-01-29).

## Decisions

- Precedence between matching profiles: a rule that names the device
  (`product_id`, `name`, `descriptor_hash`, `sdl_guid`) beats a class rule
  (OS, backend, browser mapping, vendor); then verified, then source
  (curated > report > SDL), then the number of conditions. Reason: a
  curated profile with VID/PID must beat a more detailed SDL entry, and an
  exact SDL entry must beat a generic curated fallback.
- `[[match]]` rules are alternatives (OR), fields within a rule all must
  hold (AND); `when` reuses `MatchRule` (empty = always). Reason: one
  matcher for both; mapping entries can differ by any identity field.
- Input strings follow SDL GameControllerDB (`b`, `a`, `+a`, `-a`, `~`,
  `h.mask`), with other raw sources in braces. Reason: the D2 import is
  lossless and SDL's syntax is known to curators.
- Semantics: every input is a position `t` in `[0, 1]`; buttons press at
  `t >= 0.5` (a `b` input at the provider's press threshold), sticks are
  `2t - 1`, triggers `t`, halves `-t`/`t`. Reason: it is SDL's behaviour,
  so imported entries behave as in SDL, and Gamepad API analog buttons map
  to triggers unchanged.
- `indices = "backend" | "sdl"` per profile. Reason: SDL indices are not
  HID usages or evdev codes and need a provider that reproduces SDL's order.
- `sdl_guid` rules compare without the name CRC, and without the version
  when the rule's is 0, computing the device's GUID with the rule's driver
  signature. Reason: SDL's own lookup; the identity does not know which SDL
  backend would read it.
- Calibration is only a per-axis `deadzone` for now. Reason: ranges in raw
  units depend on the backend; D3 will show what is needed, and
  `schema_version` guards later additions.
- `face` is a table of labels and falls back to the family's. Reason:
  reuses the model's `FaceLayout`; no preset names to maintain.
- No new ADR: this implements ADR 0003; the rules live in the crate docs
  and `data/profiles/README.md`.

## Open questions

- A way to unset a target in a later mapping entry (a control missing on
  one OS) is not in the format yet.
- Whether the digital trigger buttons should be derived from the trigger
  axes by the mapping engine (C3) instead of mapped explicitly, as the
  standard profile does now.
