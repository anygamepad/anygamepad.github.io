# W4: Guided mapping wizard

- Status: completed
- Roadmap: ROADMAP/2026-10-14/ (task ID: W4; dates updated in place)

## Goal

For a connected pad, a view that asks the person to use each control of the
usual layout in turn and records which raw element answers, as a mapping in
canonical terms; a button combination on the pad itself says the pad lacks
the control asked for (owner request, 2026-10-14). The logic lives in the
library so the desktop app's collection mode (A3) reuses it.

## Done

- `anygamepad::wizard`: `Wizard` (state machine fed with `RawState` and a
  time once a frame), `Step` (`Button`, `Stick`, `Trigger`; `Step::USUAL`,
  21 steps), `Status`, `Phase`, `Outcome`; `skip()`, `back()`,
  `restart()`, `mapping()` (a D1 `Mapping`), `missing()`.
  - Detection: a button past half its travel, a hat off centre, an axis
    half its range away from where it rests. Button steps take a button,
    then a hat direction, then half an axis; stick steps an axis (the one
    that moved most); trigger steps an axis, a button, or both (analog
    buttons drive the trigger axis too, digital ones only the button).
  - Rest: learned when nothing is pressed and nothing moved for 300 ms, at
    the start and while listening; a step completes when everything is
    released for 80 ms and the axis is back from its extreme. Triggers
    that rest at an end read whole (`a5`), at the centre as a half (`+a2`,
    `-a2` for a combined axis); the end an axis settles at after the press
    is its rest (browsers that report 0 until first use, then -1).
  - Elements that answered an earlier step are refused and named
    (`Status::conflict`). The bottom and right face buttons pressed
    together record the current control as missing (`Status::chord`).
- `anygamepad::mapping`: maps are filled by insertion instead of collected
  (collecting sorts, and the sort cost about 10 KiB of WebAssembly).
- `anygamepad-report` (P1 format): `UserStatement` gains `missing_buttons`
  and `missing_axes`; schema regenerated; `data/reports/README.md` example
  shows a SNES-style pad's wizard result.
- `anygamepad-wasm`: `MappingWizard` (`status()`, `results()`, `missing()`,
  `mappedState()`, `skip()`, `back()`, `restart()`), created and fed by
  `Gamepads.wizard()`/`feedWizard()` (raw Gamepad API elements) and
  `HidDevices.wizard()`/`feedWizard()` (decoded PlayStation pads, over
  their canonical controls). `ts/check.ts` covers the API.
- Web app: "Identify the buttons" in the selected pad's header (Gamepad API
  pads and decoded WebHID pads). `wizard.ts` shows the step, what was
  detected, a conflict, the combination hint (with the pad's printed
  labels, "Cross and Circle", when its family is known), the drawing with
  the control asked for marked and the mapping so far driving it, buttons
  ("Not on this pad", "Back", "Start over", "Close") and the results.
  After a finished run, the live view draws the pad through the identified
  mapping and names its raw elements. The activity log records each step,
  undo, skip and the result.
- Tests: 13 unit tests of the wizard, among them a standard pad that gives
  exactly the curated `gamepad-api-standard.toml` mapping, a DirectInput
  pad (hat d-pad, combined trigger axis, trigger resting at its minimum),
  conflicts, the combination, skip, back, restart, held controls, diagonal
  sticks, canonical sources, NaN; a test of the canonical layout in the
  bindings. The smoke test runs all 21 steps on a pad without the standard
  mapping (d-pad on axes, combination and button skips, conflict, back,
  summary, the identified mapping driving the drawing and the raw names)
  and the first steps on the fake WebHID DualSense; it checks the log.
  Passed 3 times in a row in Chromium.
- Sizes (gzip): wasm 105.3 KiB of 128 (85.6 before: the mapping engine
  enters the bundle, which W5 needs too), JS 59.7 of 64, CSS 2.7.
- Verified locally: fmt; clippy with `-D warnings` (workspace native and
  wasm32, `anygamepad` without default features, model, db and report with
  all features); workspace and all-feature tests; rustdoc with
  `-D warnings`; `cargo +1.85` checks; the `.d.ts` check; the web build,
  size budget and smoke test (Chromium; Firefox and WebKit run in CI).

## Decisions

- The skip combination is the first two buttons identified, pressed
  together. Reason: on an unknown pad nothing else is known yet; after two
  steps those two are, and every pad has them. The view has buttons for the
  same, for people at a keyboard.
- Skipping means "the pad does not have it", recorded as missing controls.
  Reason: the owner asked for a way to say so; it is data for profiles
  (P4), not a gap.
- The order puts the bottom and right face buttons first. Reason: they
  define the combination for every later step.
- A button step accepts hats and half axes. Reason: d-pads are hats
  (DirectInput) or axes (Firefox, some SNES-style pads), and the profile
  format can say so (`h0.1`, `-a1`).
- The library decides; the view only renders. Reason: A3 reuses the same
  state machine, and the native tests cover the rules.
- Decoded WebHID pads run the wizard over their canonical controls. Reason:
  it checks the decoder against real presses (the owner's DualSense on
  macOS); raw WebHID devices need a HID report parser, not planned yet.
- No new budget: the wasm grew 19.7 KiB but stays under 128 KiB; the sorts
  that collecting maps pulled in were removed instead.
